# Review and execution controls

Proposal decisions immediately remove the selected card locally and expose the next cached proposal. Outstanding and acknowledged keys are excluded from polling results; detached buttons cannot submit twice. Requests continue on navigation and the server finishes accepted decisions independently of the browser connection. Each durable Processing claim is written under the proposal gate, which is released during network work. Final queue changes reread the latest file under the gate so simultaneous decisions cannot overwrite unrelated proposals. Ambiguous failures remain visible as NeedsReview instead of being replayed. Chart aspect ratio is reserved before loading the image. Successful completions fetch the authoritative active-signal count and invalidate the parent signal center.

The shared active-signal component has timeframe tabs, counts, maximum-open controls and explicit resume. Default maximum is two per timeframe. Submitting, Submitted, Filled, Closing and RecoveryRequired reserve slots; Pending does not. The common store claim gate serializes both polling and WebSocket entry reservations. A full timeframe waits without placing another order. Entry errors that have a definite rejection become EntryError terminal results. Transport failures retain RecoveryRequired reservations rather than freeing capacity while execution is uncertain.

For limits of two or fewer, two consecutive StopLoss results block that timeframe. Another completed trade outcome resets the streak, but never clears an already latched block. Limit changes also cannot release it. Rules and processed result IDs are atomically persisted beside the queue in `.timeframe-risk.json`; result IDs prevent duplicate stop counting. Existing historical results are not retroactively replayed into the new streak. Lowering a cap does not close existing positions. Already submitting orders retain their reservations.

Blocked Pending signals expire permanently when they reach entry. Resume owns ExecutionGate, refreshes every relevant symbol price, expires any currently ready entry while the block is still active, then clears the brake and streak. Exchange trade/REST receipt timestamps also reject touches queued before the release instant, so a waiting worker cannot turn an old touch into a fresh entry. Expired signals remain terminal. Other timeframes and monitoring of filled positions continue. This uses the existing application-level entry/exit observations; it does not infer historical intrabar touches that happened while the server was offline.

Position close previews may be scoped by symbol, side and hedge index. Confirmation consumes a short-lived preview, rereads exchange size, rejects increased size, and sends the existing reduce-only market close for the approved side. No other hedge side is closed. Closing is persisted before submission; ManualClosed is emitted only after the reconciliation worker observes that side absent from exchange positions. External positions get a uniquely identified, owner-attributed audit record. Wallet snapshots are captured after confirmed closure. Close-all remains available in the heading; the redundant refresh button is hidden and automatic five-second refresh remains.

The journal displays direction without expansion. EntryError carries a reason (including insufficient available balance), and both EntryError and ManualClosed appear in events and results. The direct feed and push outbox accept both kinds. Android 1.10.0 (versionCode 22) removes the old manual-close suppression and accepts entry errors, including feed reasons. The native client advertises event version 2; older feed clients skip the new kinds while their cursor still advances, preserving existing notification delivery. Existing Android installations need the new APK for these newly introduced native notification kinds; web changes alone cannot update Java notification filtering.

Validation includes concurrent reservation caps, per-timeframe independence, configurable cap three, durable/idempotent stop streaks and resume, permanent blocked-entry expiry, typed balance-error results, selected hedge-side reduce-only requests, preview replay rejection and confirmed manual results. Browser tests cover immediate proposal advancement, duplicate clicks, polling and out-of-order response isolation, active counter refresh, timeframe settings/resume, selected-position confirmation and directional terminal journal entries. Real Chromium layout/regression tests run at mobile and desktop sizes; exchange calls and order submissions are mocked.
